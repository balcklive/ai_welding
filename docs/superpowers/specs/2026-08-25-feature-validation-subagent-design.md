# 功能验证测试与修复 Subagent 编排设计

## 目标

依据 `docs/功能验证测试清单.md`，在当前试验数据库和 MinIO 桶上逐项执行 P0、P1、P2 测试；发现问题后完成修复、针对性验证和独立代码审查，保留可追溯的测试记录。

测试账号仅从现有本地环境读取，禁止把密码写入代码、文档、报告或 git 历史。

## 执行阶段

1. **基线阶段**：确认服务依赖、健康检查、后端 pytest、前端 lint/typecheck/build，并记录初始状态。
2. **P0 业务链路**：版本管理、多模态对齐、数据切分、数据标注。
3. **P1 分析与模型**：高级信号、特征、数据集、模型、训练、测试、推理。
4. **P1 产物与稳定性**：报告、对象存储、审计、鉴权、前端容错。
5. **P2 破坏性与负载**：注入、畸形文件、并发、负载、故障恢复；使用试验数据库和现有 destructive fixtures。
6. **最终回归**：完整自动化测试、前端检查、关键链路复测和全分支审查。

每项记录测试编号、时间、执行 agent、实体/版本/Job 信息、请求/响应或页面结果、日志/对象证据、预期与实际结果、状态和复现步骤。

## Subagent 分工

每个阶段采用严格串行闭环，避免多个 agent 同时修改工作区：

- **测试 agent**：只执行和记录测试，不修改业务代码。
- **修复 agent**：针对测试报告修复代码，并补充或更新自动化测试；不得顺手处理无关问题。
- **验证 agent**：独立复现失败用例、执行修复后的针对性测试和必要回归，不修改代码。
- **审查 agent**：审查 diff、测试证据、错误处理、数据/对象幂等性和安全影响；发现问题时回到修复闭环。

主 agent 只负责编排、汇总、维护 ledger 和处理跨阶段决策，不直接代替修复 agent 修改代码。

## 数据与安全边界

- P2 允许在当前明确为试验用途的数据库和 MinIO 桶执行，但所有新增数据、Job、对象和日志必须可追溯。
- 优先使用 `backend/tests/fixtures/destructive/`，不得触碰生产环境。
- 并发和暴力尝试采用受控规模，记录响应时间、状态码、错误率和数据膨胀情况。
- 所有预期 4xx 必须确认不是 500；敏感字段在日志和报告中脱敏。
- 测试 agent 不把 token、密码或完整敏感响应写入持久化报告。

## 通过标准

- 清单用例均有明确状态：通过、失败、阻塞或不适用。
- 失败项若可修复，必须完成“测试 → 修复 → 验证 → 审查”闭环。
- 修复后后端 pytest 与前端 lint/typecheck/build 通过，且关键业务链路无回归。
- 审查遗留项必须有严重级别、影响、证据和明确处理结论。
- 最终报告列出已修复问题、无法修复/需后续处理问题和已知模拟实现边界。

## 不在本轮承诺

对齐、切分、标注、训练、测试和推理的模拟算法结果不作为算法精度验收；本轮验收其任务编排、状态、关联、产物和异常提示。
