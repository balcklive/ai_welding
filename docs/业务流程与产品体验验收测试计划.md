# ForgeLab 业务流程与产品体验验收测试计划

## 1. 目的与原则

本计划用于验收 ForgeLab 从数据进入到模型推理的完整业务闭环，同时持续评估和打磨产品流程、业务逻辑和 UI 设计。

核心流程：

```text
数据集/焊缝数据
  → 焊缝数据版本
  → 数据核验
  → 分析与标注
  → 固定数据集快照
  → 模型训练
  → 测试评估
  → 推理验证
```

测试不是以“菜单能否点击”作为主要目标，而是确认：

- 用户能否按正确顺序完成业务任务并做出正确决策。
- 每一步是否使用了正确的数据集、焊缝、焊缝版本、数据集快照和任务。
- 上游产物是否能被下游正确使用，数据和版本血缘是否完整。
- UI 是否清楚表达当前上下文、前置条件、状态、风险和下一步操作。
- 成功、失败、空数据、重试和任务中断时，用户是否知道发生了什么。

测试采用“测试 → 产品/UI 评估 → 决策 → 修改 → 受影响范围复测 → 验收”的增量闭环。已经通过且未被修改影响的功能不重复测试。

本计划不替代接口契约、算法精度、数据库约束、对象存储一致性、权限安全和压力测试；但浏览器验收必须验证真实 API、数据库、对象存储和异步 Job 在页面上的完整表现。

## 2. 测试范围与版本概念

### 2.1 范围

| 范围 | 内容 |
|---|---|
| 入口冒烟 | 登录、菜单展开/收起、页面切换、权限和前置条件提示 |
| 数据治理 | 数据集、焊缝登记/上传、焊缝版本、数据核验、报告 |
| 分析标注 | 数据选择、多模态对齐、起收弧识别、样本切分、图像/时序/视频标注、特征提取 |
| 建模闭环 | 数据集快照、模型资产、训练、测试评估、推理验证 |
| 横向能力 | 加载、错误、空状态、重复点击、刷新、快速切换、导出、任务轮询 |
| 产品体验 | 业务顺序、阶段准入、术语、上下文、操作引导、信息层级和异常恢复 |

### 2.2 两类版本必须严格区分

| 版本 | 对象 | 用途 | 允许的下游流程 |
|---|---|---|---|
| 焊缝版本 | 单条焊缝数据 | 记录原始数据、去噪、对齐、人工修正等处理历史 | 核验、分析、标注、特征提取 |
| 数据集快照 | 一组固定样本 | 固定训练/验证/测试成员，保证可复现 | 训练、测试评估、模型追溯 |

页面必须使用完整术语，不使用含义不明确的“版本”。数据集快照生成后，单条焊缝产生新版本不得悄悄替换旧快照成员；训练和测试只能选择数据集快照，不能把焊缝版本当作训练数据版本。

## 3. 角色分工与交付物

每轮只处理一个业务问题或一组明确相关的问题。角色可以由不同 Sub-agent 承担，也可以由同一执行者分时承担，但测试和验收必须保持独立。

| 角色 | 工作内容 | 必须产出 |
|---|---|---|
| 业务测试 Agent | 按当前流程实际操作，验证功能、数据、状态、任务和产物 | 操作证据、通过/失败结果、复现步骤 |
| 产品评估 Agent | 判断流程顺序、阶段准入、用户决策、术语和下一步引导是否合理 | 产品问题、建议方案、优先级 |
| UI/业务逻辑评估 Agent | 检查布局层级、上下文、状态、禁用原因、交互一致性和边界体验 | UI/交互问题、影响范围、验收标准 |
| 修改 Agent | 根据已确认的问题修改代码，不扩大范围 | 修改说明、关联文件、风险范围 |
| 复测/验收 Agent | 使用独立会话和相同业务数据验证修复，并检查受影响链路 | 复测结果、回归结果、验收结论 |

问题必须先经过产品/UI 评估，再决定是缺陷、产品调整、体验优化还是暂不处理；不允许测试 Agent 直接把所有现象都当成代码 Bug。

## 4. 测试状态与增量回归规则

每个场景都要登记以下字段：

```text
场景编号：
业务阶段：
当前状态：未测试 / 测试中 / 通过 / 失败 / 待产品决策 / 待修改 / 修改中 / 待复测 / 已验收 / 跳过
测试环境与数据：
代码版本或提交号：
问题编号：
影响范围：
最后测试时间：
测试证据：截图、日志、网络请求、任务号、下载文件
复测结论：
验收人：
```

增量规则：

1. 场景通过后，若代码、接口、数据结构、共享组件或业务规则没有变化，则保持“已验收”，后续跳过。
2. 修改 Agent 提交变更时，必须声明影响的场景、页面、接口、数据对象和下游流程。
3. 复测 Agent 只执行“修改场景 + 直接依赖场景 + 共享能力回归”，不重跑全部用例。
4. 共享能力包括登录、上下文传递、版本选择、任务轮询、错误提示、导出和通用按钮状态；修改这些能力时，必须回归所有受影响阶段。
5. 发现新问题时，先补充场景和验收标准，再修改代码，避免只针对单个页面打补丁。

## 5. 每轮执行流程

### 5.1 开始前

确认前端、后端、数据库、对象存储和 Job 执行器可用，并记录环境信息。准备一条可追踪的测试数据链：数据集、焊缝、焊缝版本、真实 CSV/图片/视频、核验结果、数据集快照、模型和独立测试集。

### 5.2 执行与评估

1. 业务测试 Agent 从当前未验收的最上游阶段开始，按业务顺序执行。
2. 每到一个阶段，先确认上游产物和上下文，再操作当前页面。
3. 记录实际结果，不以“按钮可点击”代替业务成功。
4. 产品评估 Agent 判断该阶段是否支持用户完成正确决策。
5. UI/业务逻辑评估 Agent 判断页面是否清楚表达上下文、状态和下一步。
6. 对问题定级并决定：立即修改、记录待定、接受当前设计或跳过范围外能力。

### 5.3 修改、复测与验收

```text
发现问题
  → 产品/UI 判断问题性质和优先级
  → 明确验收标准与影响范围
  → 修改 Agent 实施修改
  → 复测 Agent 使用独立会话复测
  → 执行受影响范围回归
  → 通过后标记“已验收”，否则回到问题处理
```

优先级建议：

- P0：阻断业务闭环、数据串用、版本错配、结果不可追溯或造成错误业务决策。
- P1：关键流程无法完成、错误操作可产生错误任务/数据、用户无法恢复。
- P2：交互不清楚、术语或布局不合理、非关键功能异常。
- P3：视觉细节、文案和低风险体验优化。

## 6. 阶段准入、执行和完成标准

每个阶段都必须检查“进入条件—核心动作—产物—下一阶段准入”。如果条件不满足，页面应阻止操作并给出明确原因和下一步入口。

| 阶段 | 进入条件 | 核心验证 | 完成/准入标准 |
|---|---|---|---|
| 1. 数据集/焊缝数据 | 已登录，有可用数据集或可上传文件 | 创建数据集、登记焊缝、上传真实文件、查看成员和详情 | 记录创建成功，文件和焊缝归属正确，可进入版本处理 |
| 2. 焊缝数据版本 | 已选择数据集和焊缝，存在原始数据 | 查看版本链、版本详情、处理产物和当前上下文 | 当前焊缝版本明确，历史版本可追溯 |
| 3. 数据核验 | 已选焊缝版本 | 执行核验、查看 15 项规则、状态、报告、失败和重试 | 质量结果持久化；不满足规则时明确阻断或说明可继续项 |
| 4. 分析与标注 | 核验结果和焊缝版本可用 | 多模态对齐、起收弧识别、切分、标注、特征提取 | 任务和产物关联到正确焊缝版本；完成条件清楚 |
| 5. 固定数据集快照 | 有符合规则的样本和必要标注/特征 | 选择成员、划分训练/验证/测试、检查质量、创建快照 | 快照成员、来源焊缝版本、划分和血缘固化；后续不被悄悄替换 |
| 6. 模型训练 | 有可训练快照和模型资产 | 训练配置、启动 Job、进度、日志、指标、模型版本 | 训练任务和模型版本可追溯到快照，失败可解释 |
| 7. 测试评估 | 有模型版本和独立测试快照 | 启动测试、查看指标、混淆矩阵、时延和报告 | 测试集与训练集隔离，结果关联正确模型和快照 |
| 8. 推理验证 | 有可用模型版本和合法输入 | 图片/视频推理、状态、类别、置信度、耗时和失败处理 | 推理结果、输入、模型版本和任务可追溯 |

### 阶段通用验收点

- 页面顶部或显著位置显示当前数据集、焊缝、焊缝版本、快照、模型和任务上下文（适用时）。
- API 成功只展示当前响应数据；API 失败显示错误或明确空状态，不展示过期或演示结果。
- 长任务有处理中、成功、失败和必要的重试状态；任务期间不能重复创建。
- 空状态不仅说明“没有数据”，还要说明原因和下一步操作。
- 返回、刷新、切换页面后，上下文不丢失、不串数据。

## 7. 业务场景清单

以下场景按顺序执行；每个阶段通过后即可标记已验收，后续只执行受影响回归。

### A. 入口冒烟（SMOKE）

- 登录闸门：未登录不可进入业务页面，错误凭据有明确提示，登录后进入工作空间。
- 菜单入口：数据管理、分析与标注、模型中心可展开收起，15 个子菜单能进入正确页面。
- 页面前置条件：未选择数据时，核验、版本、分析、标注、训练、测试和推理页面显示原因及返回入口。
- 系统设置：若未实现，记录产品缺口，不得判为通过；若属于本期范围，进入独立验收。

### B. 数据集与焊缝数据（DATA）

- 创建数据集：名称必填，取消不产生记录，成功后列表刷新。
- 上传数据：数据集、来源、时间、焊缝/批次和文件必填；合法 CSV/图片/视频可形成真实记录。
- 异常上传：空文件、损坏文件、不支持格式和超大文件有明确错误，不留下错误业务记录。
- 数据详情：能看到归属、样本、核验状态、当前焊缝版本和进入下游流程的入口。

### C. 焊缝版本与数据核验（VERSION / VALIDATION）

- 版本链显示版本号、处理动作、操作人、备注、关联文件和核验结果。
- 核验显示 15 项规则、质量分数、通过/警告/失败数、处理中/成功/失败状态和报告。
- 历史焊缝版本不可被新版本悄悄替换；没有快照时不得伪造快照编号。

### D. 分析与标注（ANALYSIS）

- 选择数据后，后续页面持续显示正确的数据集、焊缝和焊缝版本。
- 多模态对齐验证模态选择、时间轴、真实数据源、进度、产物、失败和重试。
- 起收弧识别验证真实 CSV 的采样率、时长、通道、时域/PSD/STFT、异常、特征和报告来源。
- 样本切分验证参数、预计数量、预览、时间轴定位、任务和产物。
- 图像、时序、视频标注验证模式切换、标签、区间/区域、AI 预标注、保存和失败提示。
- 特征提取验证信号、视觉、声音特征、统一向量、特征维度和导出结果。

### E. 固定数据集快照（SNAPSHOT）

- 选择样本并检查训练/验证/测试划分、质量、标注和模型适配条件。
- 创建快照后显示快照 ID、成员清单、来源焊缝版本、划分、质量、血缘和当前快照指针。
- 修改焊缝版本后，旧快照成员和来源版本保持不变；重新构建才产生新快照。

### F. 训练、测试与推理（MODEL）

- 模型资产可创建、查看版本和状态；失败有提示。
- 训练只能选择可训练数据集快照；启动后有任务号、进度、日志、指标、模型版本和失败状态。
- 测试必须选择模型版本和独立测试快照；结果包括准确率、召回率、F1、时延、混淆矩阵和报告。
- 推理验证合法图片/视频，显示任务状态、类别、置信度和耗时；异常文件可恢复且不重复提交。

## 8. 产品经理与 UI/业务逻辑评估表

每个阶段完成功能测试后必须回答以下问题，不能只写“页面正常”：

| 评估维度 | 判断问题 |
|---|---|
| 业务顺序 | 用户是否知道为什么现在做这一步，以及完成后要去哪一步？ |
| 阶段准入 | 条件不足时是否阻止错误操作，并解释缺什么？ |
| 决策支持 | 页面是否提供用户做判断所需的数据、质量、来源和风险？ |
| 上下文 | 数据集、焊缝、焊缝版本、快照、模型和任务是否清楚且不混淆？ |
| 数据状态 | 当前展示的是加载中、空、成功、失败还是过期数据？用户能否识别？ |
| 操作引导 | 主要操作是否突出，按钮禁用原因、返回路径和下一步是否明确？ |
| 任务体验 | 长任务是否显示进度、结果、失败原因、重试和防重复提交？ |
| 一致性 | 术语、按钮、状态、弹窗、分页、筛选和错误文案是否跨页面一致？ |
| 可追溯性 | 页面、报告和任务是否能追溯到正确输入、版本和产物？ |
| 异常恢复 | 刷新、断网、接口失败、无文件、无结果后，用户能否继续工作？ |

产品问题应写成“用户目标—当前问题—业务风险—建议方案—验收标准”，UI 问题应写成“页面/状态—观察现象—影响—修改建议—截图证据”。

## 9. 横向异常与回归

在对应业务阶段首次通过后，只在相关代码或共享能力变化时执行：

- API 不可用：页面不白屏，有错误/空状态和下一步提示。
- 快速切换和刷新：不发生旧请求覆盖新页面、上下文串用或永久 loading。
- 重复点击：上传、保存、处理、训练、测试、推理和导出不产生重复任务/记录。
- 空数据和边界：无版本、无文件、无标注、无测试结果、无可训练样本时状态明确。
- 版本切换：页面、报告、任务和产物始终对应当前选择；历史快照不被覆盖。
- 导出：核验、分析、标注、特征和测试报告的内容对应当前上下文，失败有反馈。
- 会话失效：需要重新登录，不能静默使用旧身份或提交不明任务。


建议启动和检查：

```powershell
npm install

npx playwright --version
npx playwright install chromium
```

真实链路必须确认数据库中的对象 key 在 MinIO 中确实存在，CSV 接口返回真实来源标识（如 `source=real`）。没有真实数据时，只能判定入口、空状态、表单和错误处理，不能判定分析、特征、训练、测试或推理结果正确。

## 11. 通过标准与最终报告

### 单阶段通过

- 进入条件和阻断条件符合业务规则。
- 核心动作完成，数据、版本、任务和产物上下文正确。
- 成功、失败、空状态、加载和重试行为明确。
- 产品评估和 UI/业务逻辑评估无未处理的 P0/P1 问题。
- 已保存截图、日志、任务号、请求或下载等必要证据。

### 整体闭环通过

- 八个业务阶段按顺序完成，或明确记录了有依据的跳过原因。
- 数据集快照固定且可追溯，训练/测试数据隔离。
- 模型训练、测试评估和推理均关联正确模型、快照和输入。
- P0/P1 问题全部关闭；P2/P3 有明确负责人和处理计划。
- 最近一次修改的受影响范围已由独立复测 Agent 验收。

### 最终报告必须包含

```text
本轮目标和代码版本：
已验收场景：
本轮新增/修改场景：
跳过场景及原因：
发现问题及优先级：
产品决策项：
UI/交互调整项：
修改文件和影响范围：
复测及回归结果：
剩余风险：
最终结论：通过 / 有条件通过 / 不通过
```

## 12. 场景编号建议

## 13. 详细执行手册

本章是测试人员和测试 Agent 的具体操作依据。执行时必须遵循本章顺序；不得为了“尽快通过”而直接打开下游页面、使用无来源的演示数据或只检查页面文字。

### 13.1 执行边界

测试 Agent 必须做到：

1. 先确认当前阶段和进入条件，再执行页面操作。
2. 每次操作前记录当前数据集、焊缝 ID、焊缝版本、数据集快照、模型版本和任务 ID（适用时）。
3. 每次任务完成后，检查页面结果、任务状态、数据库/API 返回和对象存储产物是否指向同一业务对象。
4. 遇到页面无法继续时，先判断是环境问题、数据前置条件不足、产品规则阻断还是代码缺陷，不得直接修改测试数据来绕过问题。
5. 发现产品流程不合理时，记录为产品/UI 问题，不擅自改变验收标准。
6. 真实数据链路和模拟算法链路必须分别记录，不能把模拟结果写成算法质量通过。

测试 Agent 不应做以下事情：

- 不以菜单全部打开作为业务闭环通过。
- 不通过 URL 或直接注入前端状态来伪造已完成的上游流程。
- 不把数据库中存在一条记录当作页面业务成功，必须确认页面能够正确使用它。
- 不把按钮可点击、页面有图表、任务有返回值当作结果正确。
- 不在没有记录影响范围的情况下修改共享组件或业务规则。
- 不重复执行已经“已验收”且没有受到变更影响的场景。

### 13.2 每个场景的标准执行格式

每个场景必须按照以下格式记录，不允许只写“通过”或“页面正常”：

```text
场景编号：
场景目标：要验证的用户业务目标
前置条件：数据、版本、账号、任务或页面状态
操作步骤：逐步记录实际操作
预期结果：功能、数据、状态、提示和下一步
实际结果：实际观察到的结果
业务判断：是否支持用户完成正确决策
UI 判断：上下文、层级、状态、引导是否清晰
证据：截图、控制台、网络、响应、任务号、文件
结论：通过 / 失败 / 待产品决策 / 跳过
问题编号及优先级：
是否需要回归：
```

## 14. 产品/UI 问题判定细则

测试 Agent 遇到以下情况，必须提交产品或 UI 评估，不得只记录为“样式问题”：

- 用户不知道当前处理的是哪个数据集、焊缝或版本。
- 页面允许执行一个按业务规则本应被阻止的操作。
- 页面阻止了操作，但没有说明原因或下一步。
- “焊缝版本”和“数据集快照”在文案、筛选器或下拉框中无法区分。
- 页面显示任务完成，但用户无法找到产物、报告或下一步入口。
- 页面展示指标，但没有数据来源、模型版本、快照或时间范围。
- 出错后只能刷新页面或重新走完整流程才能恢复。
- 页面入口顺序与实际业务顺序冲突，用户容易跳过必要阶段。
- 同一个概念在不同页面使用不同名称，导致用户可能做出错误选择。

问题记录模板：

```text
用户目标：
当前页面和状态：
实际行为：
用户可能产生的误解或错误操作：
业务风险：P0 / P1 / P2 / P3
建议调整：
验收标准：
影响页面和场景：
```

## 15. 复测与回归矩阵

修改完成后，修改 Agent 必须填写影响矩阵；复测 Agent 按矩阵执行，不凭感觉扩大或缩小范围。

| 修改类型 | 至少复测 |
|---|---|
| 单页面文案或布局 | 当前页面正常流程、空/失败状态、上下文显示 |
| 单页面表单或按钮 | 当前场景、前置条件、重复点击、成功/失败任务 |
| 数据集/焊缝选择逻辑 | 数据选择、版本、核验、分析上下文和返回路径 |
| 焊缝版本逻辑 | 版本链、核验、分析、快照成员追溯 |
| 数据集快照逻辑 | 快照创建、成员、训练配置、测试配置、旧快照不变性 |
| Job 创建/轮询逻辑 | 所有使用该 Job 能力的处理中/成功/失败/重复点击场景 |
| 通用错误/空状态组件 | 当前页面和所有使用该组件的相关页面 |
| 导出或对象存储逻辑 | 当前导出、文件存在性、上下文、失败重试 |
| 登录/权限逻辑 | 登录、登出、会话失效和所有受保护页面 |

复测通过的定义：原问题已满足验收标准，且影响矩阵中的直接依赖场景没有引入新的 P0/P1 问题。只有复测 Agent 可以将状态改为“已验收”。

### 16.2 产品评估 Agent

```text
你是产品评估 Agent。基于用户完成业务任务的目标评估当前流程。
重点判断阶段顺序、准入条件、用户决策、下一步引导、版本语义、数据不可变性和异常恢复。
不要因为页面能工作就判定产品合理，也不要把个人偏好当作缺陷。
每个问题必须说明业务风险、建议方案和可验收标准。
```

### 16.3 UI/业务逻辑评估 Agent

```text
你是 UI 与业务逻辑评估 Agent。检查上下文、信息层级、状态、禁用原因、错误提示、任务反馈、术语一致性和返回路径。
确认页面是否让用户知道当前对象、当前阶段、当前状态和下一步。
发现问题后标明页面、状态、截图证据、影响场景和回归范围。
```

### 16.4 修改 Agent

```text
你是修改 Agent。只处理已经确认的问题和验收标准。
修改前先说明涉及页面、接口、共享组件和下游影响；修改后说明文件、行为变化和风险。
不要通过隐藏错误、伪造数据或放宽业务准入来让测试通过。
```

### 16.5 复测/验收 Agent

```text
你是独立复测与验收 Agent。使用独立浏览器会话和测试数据。
执行原问题场景、直接依赖场景和修改影响矩阵中的共享能力回归。
确认原问题解决、数据和版本没有串用、失败状态可恢复。
只有证据完整且没有未处理的 P0/P1 问题时，才能标记“已验收”。
```

## 17. 最小可执行顺序

如果时间有限，必须按以下优先级执行，不能从主页面随机挑选功能：

```text
1. 环境健康检查和登录
2. 数据集 → 上传/焊缝 → 焊缝版本
3. 数据核验成功和失败路径
4. 选择数据 → 分析/标注 → 特征或样本产物
5. 固定数据集快照并验证不可变性
6. 模型训练 → 独立测试评估 → 推理验证
7. 对本轮修改执行影响范围回归
8. 更新状态、证据、问题和最终结论
```

任何阶段因环境或真实数据不足而跳过，必须记录“跳过原因、已完成的替代验证、未覆盖风险和后续补测条件”，不能记录为通过。
