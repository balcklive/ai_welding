### D1 "样本"指哪一层？（已确认：采纳 B）

结论：**样本 = 一次登记的数据（一条焊缝数据就是一个样本，不再切分）。**

由此确定的层级：

```
数据集  SP2026 焊接批次数据
│
├─ 样本 1   WLD-2026-0815-0003     <- 一次登记 = 一个样本（原来界面上叫"焊缝"）
│   └─ 数据版本链  v1.0 原始数据 → v1.1 时间对齐 → ...
│
├─ 样本 2   WLD-2026-0815-0004
│
└─ 数据集版本 v1.5                 <- 一份冻结清单，训练用它复现
    ├─ 切片 #9     来自样本 WLD-2026-0815-0003
    ├─ 切片 #10    来自样本 WLD-2026-0815-0003
    └─ ...         共 13 个切片
```

**连带改动**（本次方案影响面最大的一处，跨 4 个模块、约 15 个文件）：

1. 数据集列表与概览的"样本数"改为**数据集下的样本条数**（`weld_count`，示例中是 1），不再显示数据集版本成员数（13）
2. 数据集版本的成员在界面上改称**切片**（`Sample` / `DatasetItem` 代码标识不变）
3. 质量指标随口径改名：**有效切片占比**（分母是切片数）
4. 分析与模型中心的用词一起改，否则又会出现自相矛盾：
   - "样本分段"页的**页面内产物**改名：每个样本 → 每个切片、样本步长 → 切片步长、预计样本 → 预计切片、样本预览 → 切片预览、已创建 N 个样本 → 已创建 N 个切片（菜单名保留，见 D6）
   - 数据标注里"样本 N/M" → "切片 N/M"
   - 模型中心"全部样本/已切分样本/已标注样本/样本总数" → "全部切片/已切分切片/已标注切片/切片总数"
   - 数据总览"条焊缝数据、已标注样本" → "条样本数据、已标注切片"

**已确认的配套命名（D4 / D5 / D6）**：

- D4 数据集版本里的成员（现在的 `samples` 记录，由"样本分段"从一条样本切出来的信号窗口 / 视频抽帧）叫**切片**
- D5 样本的处理历史叫**数据版本**
- D6 分析菜单保留"样本分段"，只改页面内那几处文案

**一条提醒**：B 本身不能消除"1 与 13 同屏出现"的困惑——它俩本来就是两个层级。真正消除困惑的是另一条设计规则：**同一屏不并列展示两个层级的数量**（见 T2.4 与 T6）。

### D2 后端"可训练闸门"要不要一起删？（已确认）

结论：**只删界面结论，后端闸门保留**。

界面上的"可训练"结论要删，但后端 `datasets.status` 还是训练数据准备的真实闸门：`POST /datasets/{id}/versions/{vid}/build-tasks` 里 `if dataset.status != "可训练": return 400`，模型中心的"训练数据准备"页也依赖它。

执行口径：后端闸门保留并改名为内部概念（"可生成训练数据版本"）；错误文案改成用户能懂的话。

### D3 一期查找能力的边界（已确认 2026-09-14）

结论：**同意最小集**。

- 一期：数据集列表加"服务端分页 + 关键字搜索"；数据集版本成员表 / 全部样本表统一 20 条/页；样本选择器（顶部"当前处理数据"）改可搜索。
- 二期：组合筛选（状态、时间范围）、排序、导出、虚拟滚动。

#### T2.3 "数据质量"改为"有效切片占比" + 扣分原因

**现状不等于方案要的语义，必须重写计算逻辑**（代码依据见本节末）：

- 现有 `_compute_quality` 的 `dimension_missing_rate` = **缺失维度数 / 任务必需维度数**，是**维度级**比例，不是"缺字段的切片占比"；分母是必需维度清单的长度，与切片数无关。
- 维度判定是**按文件名/扩展名启发式**：`_dimension_availability_from_samples` 遍历样本 `object_keys`，出现任意一个时序扩展名（或 key 里含 `timeseries`/`current`/`voltage`/`gas`/`wire`）就同时认定电流、电压、气流三个字段全部具备；出现图片就同时点亮"焊缝照片"与"Molten_feature"。
- 三个比例是**已落库的标量**（`dataset_versions.quality`），没有留存每个切片的失败集合 → 现在推不出"通过全部检查的切片占比"。

改后口径：

- 有效切片占比 = **逐切片**算失败原因集合，再按去重并集统计：`effective_ratio = 未命中任何原因的切片数 / 切片总数`。`repeat_rate`、`empty_label_rate` 本身已是切片级，可直接进集合；`dimension_missing_rate` 必须按切片重算（该切片缺任一必需字段即命中）。
- **字段依据落地到真实数据，不再看文件名**：时序字段以落库的真实信号通道为准（`signal_ingests` 成功导入的 Parquet 列），视觉字段保留扩展名判定（图片/视频没有可解析的列结构）。
- **空版本**（`total == 0`）：`effective_ratio` 返回 `null`，前端显示"—"，**不得显示成 100%**（现在三个比例都是 0.0，前端一算就是 100%）。
- **单位**：`quality` 各字段继续存 0–1，展示层转百分比；`effective_ratio` 同口径，不再混用 0–100。
- **历史版本不重算**：`quality` 是构建时的快照值，接口按原样返回；重算只对新构建生效。

一期扣分原因（改后由后端返回明细，前端只负责展示）：

| 原因 | 计算口径 | 数据来源 |
| --- | --- | --- |
| 重复切片 | 同一版本内 `(record_id, object_key)` 重复出现的切片 | `samples` 行（**不再用 `frame_no`**，见 T11） |
| 空标注切片 | 版本内没有任何标注的切片 | `annotations` |
| 必需字段缺失 | 该切片缺少任务必需的输入字段 | 真实信号通道 / 对象键 |

二期可扩展原因（本次只留好数据结构）：标注未审核、AI 预标注未人工确认、采样率不一致、多模态时间戳未对齐、媒体文件缺失、样本时长越界。

#### T4.4 登记 → 上传 → 挂载 → 导入的状态与恢复

现状**不是一次提交完成**，而是四步（`RegistrationPage.handleSubmit`）：`POST /registrations` → 逐文件 `presignUpload` + PUT → `POST …/raw-files` → 后端异步 `signal_ingest`。任何一步失败都要能恢复，所以状态必须**能从后端数据推导**（刷新、换设备也能看到真实进度），不能只活在前端 state 里。

**状态定义**（全部由已有数据推导，**不新增表**）：

| 状态 | 判据 | 界面 |
| --- | --- | --- |
| 登记已创建，待上传 | 记录存在，v1.0 的 `object_keys` 为空 | "等待上传文件" + "继续上传"入口 |
| 文件已挂载，导入中 | v1.0 有 key，且存在 `signal_ingests` 行 `pending`/`running` | "导入中"（沿用 T8 的静态状态规则，不显示百分比） |
| 导入完成，可分析 | 全部 `signal_ingests` 行 `succeeded`，或本次无 CSV | "可分析" |
| 导入失败 | 任一 `signal_ingests` 行 `failed` | "导入失败" + 原因 + 重试入口 |

**"登记成功" ≠ "导入完成"**：`POST /registrations` 成功只代表记录与 v1.0 建好，核验/分析依赖的是**导入完成后的真实信号**。T4.3 的结果卡文案要区分这两件事。

**恢复规则**：

1. **上传失败**：`regRef` 已存登记，重试只重传失败文件、不重复登记（保留现有行为）。
2. **重试期间改了表单**：`regRef` 复用会丢掉新表单值。一期采用**提交期间禁用表单 + 失败后显式提示"当前登记 REG-… 已创建，修改内容需重新登记"**；不做 PATCH 回填（属 T13 编辑锁范畴）。
3. **挂载成功但响应丢失**：`attachRawFiles` 是全量幂等语义（新 key 追加、旧 key 跳过），重试同一次提交安全；但**含 CSV 时重复挂载返回 409「CSV 已存在导入任务」**——前端遇到该 409 应**按"已挂载成功"继续**（进入导入中状态），不得当失败卡住。这是现状最常见的断链点。
4. **CSV 导入失败后重试**：`signal_ingests` 对 `(version_id, source_object_key)` 幂等，**含 failed 行也会被 409 拦掉重挂**，永不自动重试（线上已踩过：旧代码失败的导入即使当前代码能解析也一直卡住）。一期提供显式"重新导入"入口——后端把该 failed 行与其 Job 清掉后重新入队，**不允许靠人工删库恢复**。

### T8 异步任务的静态状态

**问题不止"前端轮询"**：登记挂载文件会自动创建构建任务（`backend/app/api/v1/welds.py:448`），但响应只有数据版本信息、**没有 job_id**（`ok(svc.version_payload(version))`）——前端无从轮询，刷新后也无法恢复状态。

- 数据集版本创建后触发构建，前端轮询 `GET /jobs/{job_uid}`（接口已存在）
- **自动构建必须能拿到任务标识**：`create_auto_build_task` 建出的 `Job` 要随 `attach_raw_files` 的响应带出（`version_payload` 增 `build_job_id`），前端据此轮询；`GET /datasets/{id}/versions` 同样返回该字段，保证刷新后能恢复。
- 后端 `GET /datasets/{id}/versions` 增加 `build_status` 字段：`pending / building / succeeded / failed`（由 `dataset_build_tasks` join `jobs` 得出）
- **无任务 / 多次尝试的映射**：同一版本可能对应多次构建（重试）。规则：`build_status` 取该版本**最新一次**构建任务的状态；手工 `POST /versions` 建的空版本没有构建任务 → `build_status = null`，界面显示"未构建"。
- 界面显示三种静态状态：构建中 / 已完成 / 构建失败（可重试）；不显示进度百分比、不显示预计耗时
- 构建中禁用该版本的"查看切片"入口并给出说明；失败时提供"重新构建"

**重试路径必须绕过手工闸门**：手工接口 `POST /datasets/{id}/versions/{vid}/build-tasks` 有 `if dataset.status != "可训练": 400` 的闸门（`backend/app/api/v1/datasets.py:252`），而**自动构建走服务层直建任务、不经过该闸门**（`backend/app/services/datasets.py:466`）。于是首次自动构建失败后，用现有接口重试会被挡住。一期新增专用重试端点（`POST /datasets/{id}/versions/{vid}/build-tasks/retry`），复用"取消旧的 failed + 新建任务"的幂等约束，**不放开手工闸门**。

**并发守卫（会静默覆盖）**：`run_build` 末尾无条件写 `dataset.current_version_id / sample_count / status / progress`（`backend/app/services/datasets.py:900-903`）。当前 executor 是单线程顺序轮询，同进程内不会乱序；但上多 worker 或有人调 `run_job` 就会**无声覆盖**（后完成的旧任务把指针指回旧版本）。规则：**仅当 `dataset.current_version_id is None or version.id > dataset.current_version_id` 时**才更新指针与统计字段，否则只回填本次版本行。

### T10 修正切分单位：视频帧率与时序采样率必须分开

#### T10.1 现状（缺陷）

现在切分把"帧"当成了信号采样点，两个频率被当成一个：

| 位置 | 现状代码 | 后果 |
| --- | --- | --- |
| 前端统计卡 | `AlignmentWorkspace.tsx:205` 用 `stride / signals.sample_rate` 把帧换算成秒 | 页面显示"10 帧 ≈ 00:00.00" |
| 后端窗口计算 | `services/splitting.py::build_windows` 里 `total_frames = (end-start) × sample_rate`，`window_frames` / `stride_frames` 直接当采样点用 | "每个切片 10 帧"实际切出 10 个采样点 = 1 毫秒 |

按 10 kHz 采样、83 秒有效区间、步长 10 推算，会生成约 8 万个切片；按"视频帧"的正确口径应该是几百个。数量级差 200–400 倍。

#### T10.2 正确口径

两个频率是两个独立的量，各自有数据源，换算必须经过时间（秒）：

```
切片时长（秒） = 帧数 ÷ 视频帧率(fps)
信号窗口采样点数 = 切片时长（秒） × 时序采样率(Hz)
```

示例：25 fps 视频 + 10 kHz 信号 + 每个切片 10 帧

- 切片时长 = 10 ÷ 25 = **0.4 秒**
- 信号窗口 = 0.4 × 10000 = **4000 个采样点**
- 83 秒有效区间、步长 10 帧 → 约 **208 个切片**（而不是 8 万个）

两个频率在系统里都已经拿得到，不需要新增数据源：

| 量 | 来源 | 现状 |
| --- | --- | --- |
| 视频帧率 fps | `services/media_probe.py` 从 ffmpeg 解析 | 已解析出 `fps`，但切分没有使用 |
| 时序采样率 Hz | `signal_ingest._parse_fs`（从登记的 `sample_rate` 如 "10 kHz" 解析） | 已有，但被错误地当成了帧率 |

#### T10.3 改动点

**后端**

- `splitting.build_windows` 改为以**秒**为唯一基准：入参改为 `window_seconds` / `stride_seconds`，采样点窗口由 `秒 × 采样率` 推导
- `split_tasks.rules` 增加 `window_seconds`、`stride_seconds`、`video_fps`、`signal_sample_rate`，保证任务可复现
- 切片 `meta` 增加 `video_frame_no`（该切片时间中点对应的视频帧号）与 `window_seconds`
- 目标检测格式：抽帧时间点仍取窗口中点（现有逻辑不变），但窗口边界按秒计算
- 无视频时不允许按"帧"配置（见 D15）

**前端（样本分段页）**

- 切分规则增加**单位选择**：帧 / 秒
- 有视频时显示视频帧率（来自媒体探测）并允许按帧配置；无视频时禁用"帧"选项并提示原因
- 四个统计卡同时给出两种口径：`切片时长 10 帧 = 0.40 秒`、`时序窗口 4000 个采样点`
- 页面顶部来源栏把两个频率分开显示：`视频 25 fps · 时序 10 kHz`（现在只显示时序采样率）

#### T10.4 验收标准

25 fps 视频 + 10 kHz 信号、有效区间 83 秒、每个切片 10 帧、步长 10 帧：

- 预计切片数 ≈ 208（±1，误差来自首尾取整）
- 每个时序分类切片的 CSV 行数 = 4000
- 目标检测切片的 `video_frame_no` 落在 0–2075 范围内（83 × 25）
- 页面不再出现"10 帧 ≈ 00:00.00"

#### 第一批：影响一期 T1 的全局改名（D4 / D5 / D6 已确认，以下保留供查阅）

**D4 数据集版本里的成员（现在的 `samples` 记录）叫什么？**（✅ 已确认：A 切片）

- A（推荐）切片
- B 片段
- C 帧样本
- D 训练单元
- E 其他（请给词）

**D5 样本的处理历史叫什么？**（✅ 已确认：A 数据版本）

原答案 Q2 定的是"数据版本"，那是按"对象叫数据"来选的；现在对象定名"样本"，所以出现"样本的数据版本"这种轻微别扭的说法。

- A（推荐）保持"数据版本"——好处是 Q2 已定、菜单名不用再动
- B 改为"样本版本"——好处是层级关系一目了然（样本 → 样本版本），代价是菜单与文档要跟着改

**D6 分析菜单"样本分段"要不要改名？**（✅ 已确认：A，保留菜单名）

位置：左侧导航"分析与标注"下的第 4 项（路由 `analysis/split`，页面标题也叫"样本分段"）。

更正我先前的说法：**菜单名其实不矛盾**。"样本分段"可以读作"对样本做分段"，而分出来的东西正是"切片"（D4 已定名）。真正必须改的是**页面内的文案**——那里面现在用"样本"指代切出来的产物，例如"每个样本 5 帧""样本步长""预计样本""样本预览""已创建 N 个样本"，这些与新的"样本 = 一次登记的数据"冲突，要改成"切片"。

- A（推荐）菜单名保留"样本分段"，只改页面内文案——改动最小，动作名与产物名各自成立
- B 菜单改叫"样本切分"——用动词避免被读成"分段出来的样本"，语义最直白
- C 菜单改叫"数据分段"——与"数据版本"共用"数据"前缀，但与对象名"样本"不统一
- D 其他（请给词）

**顺带要核实的两个疑点**（不属决策，但会影响"切片"的实际含义）：

1. 该页"样本长度"显示 `10 帧 ≈ 00:00.00`。后端 `splitting.build_windows` 里帧 = **信号采样点**，10 kHz 下 10 个采样点 = 1 毫秒；按此推算一条 83 秒的焊缝会被切成 8 万多个切片。需要确认"帧"这个单位到底该指采样点还是视频帧——若指视频帧，切分规则与 UI 的单位换算都要修。
2. 手册截图（`docs/images/manual/11-split.png`）里"预计样本"显示 0，但页面仍可点击"预览切分结果"。需确认这是"信号未加载"的正常态还是计算缺陷。

**2026-09-14 澄清（开发人员）**：帧 = 视频帧；视频帧率远低于 10 kHz；**视频帧率与时序 CSV 的采样率是两个不同的量，必须分开处理**。据此确认第 1 条是真实缺陷，修正方案见 T10。

#### 第二批：数据模型与业务规则（D7 / D8 已确认；D9 / D10 / D15 / D16 待定）

**为什么 D7 / D8 曾被列为阻塞项**（已确认，保留作为背景）：它们不是"表单加几个必填项"，而是同时决定下面四件事，其中两件是不可逆的：

2. **后端强校验**（`RegistrationCreate` 现在除 `dataset_id`/`source` 外全是可选）——一旦上线，前端不同步会让登记功能整体不可用
3. **核验规则的实现**（见下，现有两条规则名不副实）
4. **前端表单结构**（一个输入框 vs 两个输入框 + 单位后缀）

**已核实的既有问题（决定了 D7 的性质）**：

| --- | --- | --- |
| 电流范围合理性 | `has_ts`（是否存在时序文件），**完全没读 `record.current_voltage`** | 名不副实，只要传了 CSV 就算通过 |
