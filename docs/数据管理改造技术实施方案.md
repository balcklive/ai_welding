### D1 "样本"指哪一层？（已确认：采纳 B）

结论：**样本 = 一次登记的数据（一条焊缝数据就是一个样本，不再切分）。**

由此确定的层级：

```
数据集  SP2026 焊接批次数据
│
├─ 样本 1   WLD-2026-0815-0003     <- 一次登记 = 一个样本（原来界面上叫"焊缝"）
│   └─ 数据版本链  v1.0 原始数据 → v1.1 时间对齐 → ...
│
├─ 样本 2   WLD-2026-0815-0004
│
└─ 数据集版本 v1.5                 <- 一份冻结清单，训练用它复现
    ├─ 切片 #9     来自样本 WLD-2026-0815-0003
    ├─ 切片 #10    来自样本 WLD-2026-0815-0003
    └─ ...         共 13 个切片
```

**连带改动**（本次方案影响面最大的一处，跨 4 个模块、约 15 个文件）：

1. 数据集列表与概览的"样本数"改为**数据集下的样本条数**（`weld_count`，示例中是 1），不再显示数据集版本成员数（13）
2. 数据集版本的成员在界面上改称**切片**（`Sample` / `DatasetItem` 代码标识不变）
3. 质量指标随口径改名：**有效切片占比**（分母是切片数）
4. 分析与模型中心的用词一起改，否则又会出现自相矛盾：
   - "样本分段"页的**页面内产物**改名：每个样本 → 每个切片、样本步长 → 切片步长、预计样本 → 预计切片、样本预览 → 切片预览、已创建 N 个样本 → 已创建 N 个切片（菜单名保留，见 D6）
   - 数据标注里"样本 N/M" → "切片 N/M"
   - 模型中心"全部样本/已切分样本/已标注样本/样本总数" → "全部切片/已切分切片/已标注切片/切片总数"
   - 数据总览"条焊缝数据、已标注样本" → "条样本数据、已标注切片"

**已确认的配套命名（D4 / D5 / D6）**：

- D4 数据集版本里的成员（现在的 `samples` 记录，由"样本分段"从一条样本切出来的信号窗口 / 视频抽帧）叫**切片**
- D5 样本的处理历史叫**数据版本**
- D6 分析菜单保留"样本分段"，只改页面内那几处文案

**一条提醒**：B 本身不能消除"1 与 13 同屏出现"的困惑——它俩本来就是两个层级。真正消除困惑的是另一条设计规则：**同一屏不并列展示两个层级的数量**（见 T2.4 与 T6）。

### D2 后端"可训练闸门"要不要一起删？（已确认）

结论：**只删界面结论，后端闸门保留**。

界面上的"可训练"结论要删，但后端 `datasets.status` 还是训练数据准备的真实闸门：`POST /datasets/{id}/versions/{vid}/build-tasks` 里 `if dataset.status != "可训练": return 400`，模型中心的"训练数据准备"页也依赖它。

执行口径：后端闸门保留并改名为内部概念（"可生成训练数据版本"）；错误文案改成用户能懂的话。

### D3 一期查找能力的边界（已确认 2026-09-14）

结论：**同意最小集**。

- 一期：数据集列表加"服务端分页 + 关键字搜索"；数据集版本成员表 / 全部样本表统一 20 条/页；样本选择器（顶部"当前处理数据"）改可搜索。
- 二期：组合筛选（状态、时间范围）、排序、导出、虚拟滚动。

#### T2.3 "数据质量"改为"有效切片占比" + 扣分原因

**现状不等于方案要的语义，必须重写计算逻辑**（代码依据见本节末）：

- 现有 `_compute_quality` 的 `dimension_missing_rate` = **缺失维度数 / 任务必需维度数**，是**维度级**比例，不是"缺字段的切片占比"；分母是必需维度清单的长度，与切片数无关。
- 维度判定是**按文件名/扩展名启发式**：`_dimension_availability_from_samples` 遍历样本 `object_keys`，出现任意一个时序扩展名（或 key 里含 `timeseries`/`current`/`voltage`/`gas`/`wire`）就同时认定电流、电压、气流三个字段全部具备；出现图片就同时点亮"焊缝照片"与"Molten_feature"。
- 三个比例是**已落库的标量**（`dataset_versions.quality`），没有留存每个切片的失败集合 → 现在推不出"通过全部检查的切片占比"。
- **实机核对（预置真实库，2026-09-14）**：数据集 1 当前版本存的 `repeat_rate = 0.75` 是**假象**——7 个标注锚点样本 `frame_no` 为 NULL 且属同一焊缝 → 在 `(record_id, frame_no)` 下塌成一个去重键、被判互相重复（复算结果与库中存的 0.75 完全吻合）；`dimension_missing_rate = 0.0` 同样是**假通过**——只看扩展名，一张 `raw/202.jpg` 就点亮了视觉维度。按 T11 的规则重算，同一份数据重复数为 0。实测明细见 T11。

改后口径：

- 有效切片占比 = **逐切片**算失败原因集合，再按去重并集统计：`effective_ratio = 未命中任何原因的切片数 / 切片总数`。三个明细比例都从这套集合派生（口径统一，且恒有 `rate × total == affected`）：
  - `empty_label_rate` 原本就是切片级，直接进集合；
  - `repeat_rate` 原公式 `total - len(去重键)` 只计"多余的那几条"，改为**同组重复切片每条都计**——产物相同的两条无法判断哪条是真的，两条都不算有效切片；
  - `dimension_missing_rate` 从**维度级**（缺失维度数 / 必需维度数）改为**切片级**（该切片缺任一必需字段即命中）。
- **`REQUIRED_BY_TASK` 同时驱动两处**：字段面板的"当前任务必需"标记 + 这条扣分。实现时发现「目标检测 = 电流/电压/气流速度」是抄自已删除的前端 mock，而该任务的切分产物是**抽帧 JPG**（`jobs/split.py`）→ 每个目标检测数据集都会被判 0%（实测数据集 7 的 66 个切片）。**2026-09-14 已确认改为「焊缝照片」**（目标检测的输入就是图像）。改这张表前先想清楚它的两个消费方。
- **字段依据落地到真实数据，不再看文件名**：时序字段以落库的真实信号通道为准（`signal_ingests` 成功导入的 Parquet 列），视觉字段保留扩展名判定（图片/视频没有可解析的列结构）。
- **空版本**（`total == 0`）：`effective_ratio` 返回 `null`，前端显示"—"，**不得显示成 100%**；三个明细比例保持 0.0 以兼容既有读取方（`readiness_for_version`、`dataset.progress` 等）。
- **单位**：`quality` 各字段继续存 0–1，展示层转百分比；`effective_ratio` 同口径，不再混用 0–100。
- **历史版本不重算**：`quality` 是构建时的快照值，接口按原样返回；重算只对新构建生效。

一期扣分原因（改后由后端返回明细，前端只负责展示）：

| 原因 | 计算口径 | 数据来源 |

> **更正（代码核对）**：上一版把前端推导写成"与后端 `_parse_fs` 同一套规则"不准确——`_parse_fs`（`backend/app/services/signal_ingest.py:179`）只解析**登记的 `sample_rate` 字符串**（"10 kHz"/"1kHz"/"1000"），与 CSV 无关；CSV 时间列推导是**另一段逻辑**（`_time_column_to_seconds` + `validate_signal` 的 R6 规则，`signal_ingest.py:194`）。前端要对齐的是后者，并用同一组样例做对拍。

**预置库里的真实取值形态（2026-09-14 实测）——迁移与校验规则必须覆盖**：

| 字段 | 实测值 | 影响 |
| --- | --- | --- |
| `current_voltage` | `'180A/22V'`、`'250A / 25V'`、`''`（空串） | 本文档原写"形如 `180 A / 22 V`、`180/22`、`180`"——**无空格形态也要覆盖**（`180A/22V`）；空串必须按 NULL 处理，不能落到 0 |
| `thickness` | `'6mm'` | T4.2 要求"数字，mm，0.1–200"，**存量是带单位的字符串**：校验与展示前先剥单位，否则必填校验会直接判它非法 |
| `sample_rate` | `'20K'`、`''` | **`_parse_fs` 有真实缺陷**：正则 `(\d+(?:\.\d+)?)\s*([kK])?[hH][zZ]?` **强制要求 `Hz`**，实测 `_parse_fs("20K") → None`、`_parse_fs("1000") → None`（后者连文档字符串都声称支持）。时间列缺失时信号导入靠它兜底推导采样率，必须拓宽（允许纯数字 / `20K` 写法） |

1. 默认值直接填进输入框（不是 placeholder），用户打开表单就能看见
2. 使用默认值的字段旁显示轻量标记"默认"，用户一旦修改标记消失
3. 提交前，把"仍是默认值"的字段汇总成一条确认提示：

#### T4.4 登记 → 上传 → 挂载 → 导入的状态与恢复

现状**不是一次提交完成**，而是四步（`RegistrationPage.handleSubmit`）：`POST /registrations` → 逐文件 `presignUpload` + PUT → `POST …/raw-files` → 后端异步 `signal_ingest`。任何一步失败都要能恢复，所以状态必须**能从后端数据推导**（刷新、换设备也能看到真实进度），不能只活在前端 state 里。

**状态定义**（全部由已有数据推导，**不新增表**）：

| 状态 | 判据 | 界面 |
| --- | --- | --- |
| 登记已创建，待上传 | 记录存在，v1.0 的 `object_keys` 为空 | "等待上传文件" + "继续上传"入口 |
| 文件已挂载，导入中 | v1.0 有 key，且存在 `signal_ingests` 行 `pending`/`running` | "导入中"（沿用 T8 的静态状态规则，不显示百分比） |
| 导入完成，可分析 | 全部 `signal_ingests` 行 `succeeded`，或本次无 CSV | "可分析" |
| 导入失败 | 任一 `signal_ingests` 行 `failed` | "导入失败" + 原因 + 重试入口 |

**"登记成功" ≠ "导入完成"**：`POST /registrations` 成功只代表记录与 v1.0 建好，核验/分析依赖的是**导入完成后的真实信号**。T4.3 的结果卡文案要区分这两件事。

**恢复规则**：

1. **上传失败**：`regRef` 已存登记，重试只重传失败文件、不重复登记（保留现有行为）。
2. **重试期间改了表单**：`regRef` 复用会丢掉新表单值。一期采用**提交期间禁用表单 + 失败后显式提示"当前登记 REG-… 已创建，修改内容需重新登记"**；不做 PATCH 回填（属 T13 编辑锁范畴）。
3. **挂载成功但响应丢失**：`attachRawFiles` 是全量幂等语义（新 key 追加、旧 key 跳过），重试同一次提交安全；但**含 CSV 时重复挂载返回 409「CSV 已存在导入任务」**——前端遇到该 409 应**按"已挂载成功"继续**（进入导入中状态），不得当失败卡住。这是现状最常见的断链点。
4. **CSV 导入失败后重试**：`signal_ingests` 对 `(version_id, source_object_key)` 幂等，**含 failed 行也会被 409 拦掉重挂**，永不自动重试（线上已踩过：旧代码失败的导入即使当前代码能解析也一直卡住）。一期提供显式"重新导入"入口——后端把该 failed 行与其 Job 清掉后重新入队，**不允许靠人工删库恢复**。

### T8 异步任务的静态状态

**问题不止"前端轮询"**：登记挂载文件会自动创建构建任务（`backend/app/api/v1/welds.py:448`），但响应只有数据版本信息、**没有 job_id**（`ok(svc.version_payload(version))`）——前端无从轮询，刷新后也无法恢复状态。

- 数据集版本创建后触发构建，前端轮询 `GET /jobs/{job_uid}`（接口已存在）
- **自动构建必须能拿到任务标识**：`create_auto_build_task` 建出的 `Job` 要随 `attach_raw_files` 的响应带出（`version_payload` 增 `build_job_id`），前端据此轮询；`GET /datasets/{id}/versions` 同样返回该字段，保证刷新后能恢复。
- 后端 `GET /datasets/{id}/versions` 增加 `build_status` 字段：`pending / building / succeeded / failed`（由 `dataset_build_tasks` join `jobs` 得出）
- **无任务 / 多次尝试的映射**：同一版本可能对应多次构建（重试）。规则：`build_status` 取该版本**最新一次**构建任务的状态；手工 `POST /versions` 建的空版本没有构建任务 → `build_status = null`，界面显示"未构建"。
- 界面显示三种静态状态：构建中 / 已完成 / 构建失败（可重试）；不显示进度百分比、不显示预计耗时
- 构建中禁用该版本的"查看切片"入口并给出说明；失败时提供"重新构建"

**重试路径必须绕过手工闸门**：手工接口 `POST /datasets/{id}/versions/{vid}/build-tasks` 有 `if dataset.status != "可训练": 400` 的闸门（`backend/app/api/v1/datasets.py:252`），而**自动构建走服务层直建任务、不经过该闸门**（`backend/app/services/datasets.py:466`）。于是首次自动构建失败后，用现有接口重试会被挡住。一期新增专用重试端点（`POST /datasets/{id}/versions/{vid}/build-tasks/retry`），复用"取消旧的 failed + 新建任务"的幂等约束，**不放开手工闸门**。

**并发守卫（会静默覆盖）**：`run_build` 末尾无条件写 `dataset.current_version_id / sample_count / status / progress`（`backend/app/services/datasets.py:900-903`）。当前 executor 是单线程顺序轮询，同进程内不会乱序；但上多 worker 或有人调 `run_job` 就会**无声覆盖**（后完成的旧任务把指针指回旧版本）。规则：**仅当 `dataset.current_version_id is None or version.id > dataset.current_version_id` 时**才更新指针与统计字段，否则只回填本次版本行。

### T10 修正切分单位：视频帧率与时序采样率必须分开

#### T10.1 现状（缺陷）

现在切分把"帧"当成了信号采样点，两个频率被当成一个：

| 位置 | 现状代码 | 后果 |
| --- | --- | --- |
| 前端统计卡 | `AlignmentWorkspace.tsx:205` 用 `stride / signals.sample_rate` 把帧换算成秒 | 页面显示"10 帧 ≈ 00:00.00" |
| 后端窗口计算 | `services/splitting.py::build_windows` 里 `total_frames = (end-start) × sample_rate`，`window_frames` / `stride_frames` 直接当采样点用 | "每个切片 10 帧"实际切出 10 个采样点 = 1 毫秒 |

按 10 kHz 采样、83 秒有效区间、步长 10 推算，会生成约 8 万个切片；按"视频帧"的正确口径应该是几百个。数量级差 200–400 倍。

#### T10.2 正确口径

两个频率是两个独立的量，各自有数据源，换算必须经过时间（秒）：

```
切片时长（秒） = 帧数 ÷ 视频帧率(fps)
信号窗口采样点数 = 切片时长（秒） × 时序采样率(Hz)
```

示例：25 fps 视频 + 10 kHz 信号 + 每个切片 10 帧

- 切片时长 = 10 ÷ 25 = **0.4 秒**
- 信号窗口 = 0.4 × 10000 = **4000 个采样点**
- 83 秒有效区间、步长 10 帧 → **207 个切片**（而不是 8 万个），尾片丢弃（D20，验收数字见 T10.4）

两个频率在系统里都已经拿得到，不需要新增数据源：

| 量 | 来源 | 现状 |
| --- | --- | --- |
| 视频帧率 fps | `services/media_probe.py` 从 ffmpeg 解析 | 已解析出 `fps`，但切分没有使用 |
| 时序采样率 Hz | `signal_ingest._parse_fs`（从登记的 `sample_rate` 如 "10 kHz" 解析） | 已有，但被错误地当成了帧率 |

#### T10.3 改动点

**后端（改动点不止 `build_windows`）**

`fixed_rate` / `stride` 贯穿整条链路，只改窗口计算会出现"预览 207、执行 8 万"这类不一致：

| # | 位置 | 改动 |
| --- | --- | --- |
| 1 | `backend/app/services/splitting.py:49`（`build_windows`） | 以**秒**为唯一基准：入参改 `window_seconds` / `stride_seconds`，采样点窗口由 `秒 × 采样率` 推导；只保留完整窗口（D20） |
| 2 | `backend/app/api/v1/analysis.py:111`（`SplitPreviewRequest` / `SplitTaskCreate`） | 请求体增加 `unit`（`frame`/`second`），保留 `fixed_rate` 兼容旧客户端 |
| 3 | `backend/app/api/v1/analysis.py:701,761`（预览 + 任务端点） | **单位换算收敛为一个共用函数**，两处共用；换算后的规则才参与幂等计算 |
| 4 | `backend/app/api/v1/analysis.py:791`（`rules` 字典） | 增加 `window_seconds`、`stride_seconds`、`video_fps`、`signal_sample_rate`、**`rules_version`**；`rules_version` 进 `_split_request_key` |

其余规则：

- 切片 `meta` 增加 `video_frame_no`（切片时间中点对应的视频帧号）与 `window_seconds`
- 目标检测格式：抽帧时间点仍取窗口中点（现有逻辑不变），但窗口边界按秒计算
- 无视频时不允许按"帧"配置（D15）
- **取整规则写死**：切片起点 = `round(i × stride_seconds × sample_rate)`，窗口长度 = `round(window_seconds × sample_rate)`；非整数 fps（如 29.97）帧→秒用 `帧数 / fps`，**不做整数截断**，避免累积漂移
- **视频与信号起点不一致 / 时长不同**：一期以**信号时间轴为唯一基准**——事件边界来自信号（`event_bounds`），fps 只用于"帧 ↔ 秒"换算与 `video_frame_no`；视频短于信号时该切片抽帧失败按现有部分失败语义跳过并告警（`jobs/split.py:68`）；`fps` 探测失败则**禁用"帧"单位**并提示原因，不猜默认值

**前端（样本分段页）**

- 切分规则增加**单位选择**：帧 / 秒
- 有视频时显示视频帧率（来自媒体探测）并允许按帧配置；无视频时禁用"帧"选项并提示原因
- 四个统计卡同时给出两种口径：`切片时长 10 帧 = 0.40 秒`、`时序窗口 4000 个采样点`
- 页面顶部来源栏把两个频率分开显示：`视频 25 fps · 时序 10 kHz`（现在只显示时序采样率）

#### T10.4 验收标准

25 fps 视频 + 10 kHz 信号、有效区间 83 秒、每个切片 10 帧（= 0.4 秒）、步长 10 帧（= 0.4 秒）：

- 预计切片数 = **207**（`1 + floor((83 − 0.4) / 0.4)`）。原"约 208"把不足一个窗口的尾片也算进去了，与下一条自相矛盾；尾片按 **D20 丢弃**，切片全部等长
- 每个时序分类切片的 CSV = **4000 数据行**（另含 1 行表头，文件共 4001 行）
- 目标检测切片的 `video_frame_no` 落在 0–2075 范围内（83 × 25）
- 页面不再出现"10 帧 ≈ 00:00.00"
- **回归项**：同一组参数下"预览切片数"与"任务完成后的 `sample_count`"必须一致

### T11 数据集构建的成员来源与重复判定（D16 的前置条件）——**已实现（2026-09-14）**

**方案的隐含前提与代码不符**：方案假设"数据集成员都是样本分段切出来的切片"，实际 `_samples_for_dataset_records`（`backend/app/services/datasets.py:964`）的行为是：

1. 该数据集下**全部** `Sample` 都收——`select(Sample)` 全表读后按 `record_id` 归属，**不区分是哪一次分段任务的产物**；
2. 某条登记数据**没有任何 Sample** 时，用它的 latest 数据版本 `object_keys` **新建一条基础 Sample**（`frame_no=0`、`meta.source="dataset_record"`），直接引用原始文件。

于是选 D16-A（保留历史 + 重新切分）后，**基础成员 + 旧切片 + 新切片会一起进入后续数据集版本**。

**更硬的坑**：分段写入的 `frame_no` 是**任务内序号**（`backend/app/jobs/split.py:90`，`enumerate(windows, start=1)`），不是真实视频帧号。两个分段任务在同一条焊缝上产生的 `frame_no` 序列**完全重合**，而质量计算的重复判定正是 `(record_id, frame_no)`（`backend/app/services/datasets.py:1066`）→ repeat_rate 直接跳到 ~50%，还会被当成真实质量问题展示。所以 D16-A 不是独立可选项，**必须先做完 T11**。

**实机核对（2026-09-14，预置真实库）**——数据集 1（`SP2026…`，`status=可训练`，`current_version_id=12`）的构建候选共 **8 个**，来源是 **7 个标注锚点样本 + 1 个基础样本，没有一个分段切片**：

| 事实 | 实测结果 |
| --- | --- |
| 版本 v1.6 成员构成 | 7 × `meta.source=signal-anchor`/`video-anchor` + 1 × `dataset_record` |
| 锚点样本 `frame_no` | **NULL**（不是 0），且 `object_keys` 为空（signal/video 标的推流桥未落地） |
| 库中 `dataset_versions.quality.repeat_rate` | v1.2 → v1.6 = **0.75 / 0.7 / 0.7692 / 0.7692 / 0.75** |
| 同库 `samples` 总量构成 | 100 锚点 + 66 切片（1 个分段任务）+ 3 基础样本 |

**这些 repeat_rate 全是假的**。同一焊缝的 7 个锚点样本 `record_id` 相同、`frame_no` 都是 NULL → 在 `_compute_quality` 里**全部塌成一个去重键**，被算成"互相重复"。实测复算：去重键 2 个 → 判重复 6 个 → `repeat_rate = 0.75`，与库中存的 0.75 完全吻合；同一份数据换成"有产物才判重"的规则，去重键 8 个、**重复 0**。

两个数据集正好各暴露一半问题（同一份实测）：

| 数据集 | 下一次构建会收到 | 症状 |
| --- | --- | --- |
| 1（`SP2026…`，仅 1 条登记） | 7 锚点 + 1 基础样本 = **8**，**0 个切片** | **成员构成错**：锚点样本当切片，且 `repeat_rate` 假报 0.75 |
| 7（`药芯…`，仅 1 条登记） | 66 切片 + **1 个陈旧基础样本** = **67**（该基础样本是分段**之前**那次构建留下的，`object_keys` 指向旧版本） | **成员数会从 1 跳到 67**：基础成员与新切片并存、且指向不同数据版本 |

**结论修正**：真正的第一因不是"分段任务撞号"，而是**成员收集根本没有来源白名单**——线上还没走到分段撞号那一步，就已经同时出现"锚点样本冒充切片"（数据集 1）和"陈旧基础样本与切片并存"（数据集 7）。数据集 7 这一幕**不需要等 D16-A**：只要用户重新点一次构建就会发生。因此 T11 的两条修复缺一不可：**成员来源白名单** + **判重规则的"无产物视为唯一"**。

**改后规则**：

| 项 | 规则 |
| --- | --- |
| 成员来源白名单 | `dataset_records` 来源下**只收两类**：分段任务的切片、登记数据的基础样本。**明确排除标注锚点样本**（`meta.source` 以 `-anchor` 结尾 / 只有 `annotation_task_id` 且无 `object_key` 的样本）——它们不是切片，是标注工作台的锚点。用户显式选 `source=annotation_task` 时才收 |
| 每条登记数据二选一 | 存在成功的分段任务 → 取**最近一次**成功分段任务的切片；否则 → 取基础样本（引用 latest 版本原始文件）。**不得混合**，也不得再"有多少收多少" |
| 基础成员的命名 | 基础样本也算"切片"（成员表统一按切片展示），但 `meta` 标 `source="dataset_record"`，界面提示"该成员未切分，直接引用原始数据" |
| 数据版本选择 | 基础样本引用 `record.latest_version_id`（与 Q9 已确认的"最新版本"口径一致） |
| 分段任务选择 | 取该焊缝 version 链上 **status 成功 + created_at 最新** 的一个；旧任务的切片不进版本（仍在库里，即 D16-A 的"历史切片"） |
| 重复判定 | 改用 `(record_id, object_keys)`；**`object_keys` 为空的样本一律视为唯一**（不参与判重）——否则空产物又会塌成一个键，重复 T11 要修的错。`frame_no` 仅作展示，不参与判重 |
| rules_version | 切片 `meta` 记录生成它的 `rules_version`（T10），供 D16-A 的"标记规则版本"使用 |
| 成员数量保护 | 单版本成员数设软上限 + 构建前提示（误配规则会一次产出天量切片），超过则要求用户确认 |

> **顺带修一个分组漏洞**：`_sample_record_id`（`backend/app/services/datasets.py:1250`）对锚点样本只能靠 `meta.weld_id` 反查焊缝；查不到的（实测存在 `meta={'source':'manual-import'}`、连 `weld_id` 都没有的样本）会返回 `None`，而 `run_build` 把 `None` 归成 `("orphan", sample_id)` → **每个孤儿自成一个"焊缝"组**，8:1:1 的防泄漏分组对它们完全失效（同一焊缝的样本可能同时进 train 和 test）。成员来源白名单落地后这类样本不再进版本，但分组侧仍应加一条断言/告警：`record_id is None` 的成员数 > 0 时记录警告。

**代码依据**：`backend/app/services/datasets.py:964`（成员收集）、`:1053`（重复判定）、`backend/app/jobs/split.py:90`（`frame_no` 语义）。

**D5 样本的处理历史叫什么？**（✅ 已确认：A 数据版本）

原答案 Q2 定的是"数据版本"，那是按"对象叫数据"来选的；现在对象定名"样本"，所以出现"样本的数据版本"这种轻微别扭的说法。

- B 改为"样本版本"——好处是层级关系一目了然（样本 → 样本版本），代价是菜单与文档要跟着改

**D6 分析菜单"样本分段"要不要改名？**（✅ 已确认：A，保留菜单名）

位置：左侧导航"分析与标注"下的第 4 项（路由 `analysis/split`，页面标题也叫"样本分段"）。

更正我先前的说法：**菜单名其实不矛盾**。"样本分段"可以读作"对样本做分段"，而分出来的东西正是"切片"（D4 已定名）。真正必须改的是**页面内的文案**——那里面现在用"样本"指代切出来的产物，例如"每个样本 5 帧""样本步长""预计样本""样本预览""已创建 N 个样本"，这些与新的"样本 = 一次登记的数据"冲突，要改成"切片"。

- A（推荐）菜单名保留"样本分段"，只改页面内文案——改动最小，动作名与产物名各自成立
- B 菜单改叫"样本切分"——用动词避免被读成"分段出来的样本"，语义最直白
- C 菜单改叫"数据分段"——与"数据版本"共用"数据"前缀，但与对象名"样本"不统一
- D 其他（请给词）

**顺带要核实的两个疑点**（不属决策，但会影响"切片"的实际含义）：

1. 该页"样本长度"显示 `10 帧 ≈ 00:00.00`。后端 `splitting.build_windows` 里帧 = **信号采样点**，10 kHz 下 10 个采样点 = 1 毫秒；按此推算一条 83 秒的焊缝会被切成 8 万多个切片。需要确认"帧"这个单位到底该指采样点还是视频帧——若指视频帧，切分规则与 UI 的单位换算都要修。
2. 手册截图（`docs/images/manual/11-split.png`）里"预计样本"显示 0，但页面仍可点击"预览切分结果"。需确认这是"信号未加载"的正常态还是计算缺陷。

**2026-09-14 澄清（开发人员）**：帧 = 视频帧；视频帧率远低于 10 kHz；**视频帧率与时序 CSV 的采样率是两个不同的量，必须分开处理**。据此确认第 1 条是真实缺陷，修正方案见 T10。

#### 第二批：数据模型与业务规则（D7 / D8 / D15–D20 已确认；D9 / D10 待定）

**为什么 D7 / D8 曾被列为阻塞项**（已确认，保留作为背景）：它们不是"表单加几个必填项"，而是同时决定下面四件事，其中两件是不可逆的：

- **A（推荐，已采纳）无视频时按"秒 / 毫秒"配置切分规则；有视频时才额外提供"帧"**

**D16 已经按旧规则切出来的历史切片怎么处理？**（✅ 已确认：A，影响 T10）

- B 一次性清理历史切片，全部重新切分
- C 不处理，只保证新数据正确
