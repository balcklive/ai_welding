# 数据库表结构设计 — 焊接数据智能分析与 AI 建模平台

> 版本：v0.1（设计稿） · 日期：2026-08-23 · 状态：待实现
>
> 数据库：**MySQL 8.4**（远程，连接见 `.env`），字符集 `utf8mb4`，引擎 InnoDB。
> 后端 ORM：**SQLModel**（SQLAlchemy + Pydantic），迁移：**Alembic**。
> 本设计对应 `docs/API接口清单.md` 的核心实体与接口参数。

---

## 1. 设计决策

| 决策点 | 结论 |
|---|---|
| 主键 | 全部自增 `BIGINT` 主键 `id`；对外 API 使用**业务标识**（`weld_id`/`registration_no`/`job_uid` 等字符串），存为唯一列 |
| 命名 | 表名 snake_case 复数；列名 snake_case |
| 时间 | `created_at`/`updated_at` 均为 `DATETIME(6)`，统一存 UTC |
| 状态 | `VARCHAR(32)` + 注释枚举值（不用 ENUM，便于迁移扩展） |
| 结构化多变数据 | JSON 列（模态列表、框坐标、指标、切分、事件、超参、结果等） |
| 外键 | InnoDB 物理外键；`jobs` 与各任务表为 **1:1**（任务即 Job） |
| 异步任务 | 统一 `jobs` 表承载生命周期（对应 `GET /jobs/{id}`），各任务表存领域数据并引用 `job_id` |
| 冗余列 | `data_records.latest_version_id`、`datasets.current_version_id` 为**反规范化冗余**，由"新建版本"服务维护，避免列表页每次都查 max(version) |
| 软删除 | 暂不需要（版本/快照机制已保证可追溯） |

## 2. 关系总览

```
users ─── 1:N ─── data_records ─── 1:N ─── data_versions ─── 1:1 ─── validation_reports ─── 1:N ─── validation_rule_results
                    │                     │
                    │                     └── 1:N ─── alignment_tasks / split_tasks / feature_extractions
                    └───── 1:N ─── (对象) samples ─── 1:N ─── annotations
split_tasks ─── 1:N ─── samples ─── N:1 ─── annotation_tasks（标注任务，1:1 关联 jobs）
datasets ─── 1:N ─── dataset_versions ─── 1:N ─── dataset_items ─── N:1 ─── samples
models ─── 1:N ─── model_versions
jobs ─── 1:1 ─── alignment_tasks / split_tasks / annotation_tasks / training_tasks / test_tasks / inference_tasks / dataset_build_tasks
```

## 5. 关键业务逻辑落地

- **"数据列表只显示最新版本"**：`GET /welds` 直接查 `data_records`（含 `latest_version_id` 反规范化列），无需聚合 `data_versions`。
- **版本链**：`GET /welds/{id}/versions` 按 `created_at` 查 `data_versions`；新建版本时事务内：插入 `data_versions` → 更新 `data_records.latest_version_id`。
- **登记与原始文件**：`POST /registrations` 事务内插入 `data_records` + `data_versions`(v1.0, action=原始数据) + 更新 `latest_version_id`；上传完成后 `POST …/raw-files` 回填 `data_versions.object_keys` 并累加 `data_records.storage_bytes`（原始文件归属版本，保证可回放/下载）。
- **标注任务**：`POST /annotation-tasks` 创建 `jobs`(type=annotation, pending) + `annotation_tasks`（1:1），并把来源切分样本的 `samples.annotation_task_id` 指向新任务；进度随标注提交回填。
- **核验**：核验报告（report）+ 规则明细（rule_results）分两张表；`POST …/validation` 同步执行后写入。
- **异步任务**：创建时插入 `jobs`（pending）+ 对应任务表（1:1）→ 返回 `job_uid`；轮询 `GET /jobs/{job_uid}` 只读 `jobs` 状态；成功后结果 JSON 回填 `jobs.result` 与任务表领域字段。
- **数据集固定快照**：构建任务成功后，`dataset_items` 落库固定 `(dataset_version_id, sample_id, split)`；原始数据变化**不覆盖旧版本**，而是新建 `dataset_versions`，保证历史训练可复现。
- **按焊缝 ID 划分**：划分策略由构建服务按 `samples` 所属 `data_records` 分组实现，避免同焊缝样本泄漏到多个分片（对应 README 规则）。
- **版本产生规则**：`POST /registrations` 生成 v1.0（原始数据）；`POST /welds/{id}/versions` 生成加工版本（去噪处理/人工修正，body 带 `action`/`object_keys`）；**对齐任务成功**后由对齐服务自动生成 `action=时间对齐` 版本。以上每次新建版本均在同一事务内更新 `data_records.latest_version_id`。
- **核验联动质量状态**：`POST …/validation` 同步执行后，按规则回写 `data_records.quality`：失败>0→异常、仅警告→待复核、否则→通过；`data_versions` 不冗余该字段，列表 `GET /welds` 直接读 `data_records.quality`。
- **训练产出模型版本**：训练任务成功（`jobs.status=succeeded`）时，事务内插入 `model_versions`（`status=实验版本`）+ 权重写 MinIO `models/{model_version_id}/weights.pt`；后续由 `PATCH /models/{id}/versions/{vid}` 手动流转为生产候选。
- **数据集质量计算**：构建任务成功后由构建服务计算质量指标（重复率/空标注率/维度缺失）写入 `dataset_versions.quality`。
