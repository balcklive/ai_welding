# 工程大文件切割方案

## 1. 目标与边界

本方案只调整代码组织和依赖方向，不改变现有 API 路径、请求/响应结构、数据库 schema、页面视觉和业务流程。采用渐进迁移，每个 PR 都必须可独立构建、测试和回滚，不做一次性“大爆炸”重构。

当前主要热点：

| 文件 | 当前规模 | 主要问题 |
| --- | ---: | --- |
| `src/App.tsx` | 约 3,100 行 / 295 KB | 应用壳、导航、页面、图表、上传、任务状态混在一起 |
| `src/index.css` | 约 104 KB | 全局样式与全部业务页面样式共享命名空间 |
| `backend/app/api/v1/analysis.py` | 约 1,420 行 | 对齐、信号、切分、标注、特征路由混合 |
| `backend/app/services/datasets.py` | 约 1,120 行 | 查询、版本、构建、就绪检查、血缘混合 |
| `backend/app/services/welds.py` | 约 775 行 | 登记、版本、核验、删除和 ACL 混合 |

建议规模目标不是硬性 KPI，但用于阻止再次膨胀：页面/复杂组件尽量不超过 400 行，Hook 不超过 200 行，路由模块不超过 300 行，服务模块不超过 500 行。超过时必须说明原因或继续按用例拆分。

## 2. 统一依赖方向

```text
前端：app/routes → features → shared → api/types
后端：api → services → models/storage/integrations
                    ↑
                  jobs
```

- 前端业务 feature 之间不直接导入内部组件，通过 app 层上下文或公开 `index.ts` 交互。
- 后端 API 不承载业务计算；service 不反向依赖 API；job 调用 service 或领域纯函数。
- 禁止新增含义模糊的巨型 `utils.ts`、`helpers.py`、`common.py`。共享代码必须有明确主题。
- 切割期间保留 `src/api/` 作为稳定接口边界，避免页面拆分与 API 重写同时发生。

### 前端状态归属

- URL/路由：当前页面、datasetId、weldId、versionId、任务 ID，后续可自然接入 React Router。
- App Context：当前登录用户和跨页面的数据选择上下文。
- Feature Hook：页面请求、loading/error、表单和任务轮询。
- 组件本地 state：弹窗、展开收起、临时绘图状态。
- 不在切割阶段引入 Redux；只有出现多个远距离消费者和复杂状态流后再评估。

### 前端迁移顺序

1. 先迁移纯类型、映射函数、格式化函数和 SVG/信号计算函数；不改 JSX。
2. 提取 `AppShell`、导航定义、公共 Toolbar/Dialog/Status 组件。
3. 按 `overview → datasets → welds` 拆低耦合页面。
4. 按 `alignment → signals → splitting → features` 拆分析页面和图表。
5. 将 image/signal/video 三种标注模式拆为独立 feature，共享标签和保存适配器。
6. 拆模型中心；训练、测试和推理各自只消费统一 Job Hook。
7. 最后按 feature 拆 CSS；先搬运原规则，再逐步引入 CSS Modules，避免视觉回归与结构重构混在同一 PR。
8. `App.tsx` 最终只保留认证闸门、Router 和顶层 Provider，目标小于 200 行。

### 后端切割规则

- Pydantic 请求/响应模型从路由文件迁到 `schemas/`，路由只保留依赖、参数和信封转换。
- 查询与写命令分文件；只有写命令拥有 commit 决策，纯计算函数不得 commit。
- ownership、幂等 key 和资源解析按业务域集中，禁止每个端点复制一份。
- `api/v1/analysis.py` 迁移成同名 package 时必须一次性完成文件到目录的切换，不能让 `analysis.py` 与 `analysis/` 并存。
- 原 router 聚合入口和所有 URL 保持不变；外部只导入各 package 暴露的 `router`。
- Job handler 文件暂不合并进 service；handler 负责生命周期，service 负责业务计算和持久化。

### 后端迁移顺序

1. 提取 schemas 和无副作用 serializer/helper，并保持旧模块 re-export，减少调用方震荡。
2. 将 `api/v1/analysis.py` 切成 analysis package，逐组迁移路由并验证 OpenAPI 路径无变化。
3. 拆 `services/datasets.py`：先 queries/serializers，再 versions/build/readiness/lineage。
4. 拆 `services/welds.py`：先 ownership/queries，再 registration/version/validation/delete 命令。
5. 最后拆模型中心服务；这一阶段与真实训练内核演进分开提交。
6. 每完成一个域，删除旧 re-export 和死代码，避免形成永久兼容层。

## 5. PR 与验收策略

每个切割 PR 只处理一个业务域或一种横切组件。纯文件移动可以较大，但不得夹带功能改造。

每个 PR 必须满足：

- API 路径与 OpenAPI operation 数量不变。
- 前端 lint、typecheck、build 通过。
- 对应前端回归测试和后端 pytest 通过。
- 页面关键路径做一次 Playwright 截图或交互冒烟。
- diff 应主要体现搬迁，不出现无关业务重写。
- 新旧模块不能长期双写状态或双实现业务逻辑。

## 6. 建议拆分批次

| 批次 | 范围 | 风险 | 预期结果 |
| --- | --- | --- | --- |
| 1 | 前端纯函数、公共组件、AppShell | 低 | `App.tsx` 降到约 2,400 行 |
| 2 | datasets + welds 页面 | 中 | `App.tsx` 降到约 1,500 行 |
| 3 | analysis charts + alignment/splitting | 中 | `App.tsx` 降到约 800 行 |
| 4 | annotation + model center + CSS | 高 | `App.tsx` 小于 200 行 |
| 5 | 后端 analysis 路由 package | 中 | 单路由模块均小于 300 行 |
| 6 | datasets/welds service package | 高 | 查询、命令、构建、ACL 边界清晰 |
| 7 | 清理兼容层和补架构约束 | 低 | 无旧入口、无循环依赖、文档同步 |

前端和后端的大文件切割不要在同一个 PR 同时进行。先稳定前端边界，再按同一业务词汇切后端，可以降低联调和回滚成本。
