# 模型中心开源集成评估与落地方案

## 结论

主方案选择 MLflow，采用“现有业务模型和 UI + MLflow 实验追踪/产物管理”的渐进式集成。当前阶段运行在 FastAPI 进程内，后续可仅通过配置切换到独立 Tracking Server。
不复制 MLflow 的前端、数据库表或内部 Store 实现；只使用 MLflow 的公开 Python 客户端和 Tracking Server。

选择依据：当前项目已经拥有焊缝、模态、样本、数据集快照、Job、MinIO 和模型版本等领域模型，缺口主要是训练实验记录、真实评估产物、可复现元数据和后续模型注册。MLflow 能以远程服务方式接入，不要求把业务数据库迁移到它的 schema。

## 当前项目与 MLflow 的映射

| 当前对象 | MLflow 对象 | 保留/迁移策略 |
|---|---|---|
| `dataset_versions` / `dataset_items` | Run tags、Dataset metadata、artifact manifest | 业务库继续作为数据快照权威；MLflow 记录快照 ID 和清单摘要 |
| `training_tasks` | Run | 每个训练任务一个 Run；超参为 Params，指标为 Metrics |
| `loss_curve` | JSON/图表 Artifact | 记录为 `model-center/loss_curve.json`，后续可补充 PNG |
| `model_versions` | Registered Model / Model Version | 当前阶段业务表仍为权威；真实模型产物接入后再创建 MLflow Model Version |
| `test_tasks` | Evaluation Run | 指标为 Metrics，混淆矩阵和报告为 Artifacts |
| `inference_tasks` | Inference Run | 记录模型版本、输入类型、延迟和结果摘要；不把每次输入样本全部复制到 MLflow |
| `jobs` | Run tags | `job_uid` 作为外部关联键，Job 状态仍由现有执行器管理 |
| MinIO | MLflow artifact store | 复用现有对象存储；MLflow 元数据与大文件分离 |

## 具体复用的 MLflow 源码/能力

### 应该复用的公开能力

1. `mlflow.tracking.MlflowClient`：查询实验、Run、模型版本和标签。
2. `mlflow.start_run`、`log_params`、`log_metrics`、`log_artifact`、`set_tags`：记录模型中心任务。
3. `mlflow.models.evaluate`：真实测试内核接入后生成标准指标和可视化。
4. Tracking Server 的 backend/artifact store 架构：MySQL/PostgreSQL 保存元数据，MinIO/S3 保存模型、曲线、混淆矩阵和报告。

### 明确不应复制的内部源码

- `mlflow/store/tracking/sqlalchemy_store.py`
- `mlflow/store/artifact/*`
- `mlflow/server/*`
- MLflow Web UI
- MLflow 数据库迁移脚本

这些目录属于 MLflow 自己的服务实现，直接复制会失去升级能力，也不能自动适配焊缝和多模态数据模型。它们应通过独立 MLflow Server 进程运行。

## 已落地的第一阶段集成

已新增：

- `backend/app/integrations/mlflow.py`：支持 `embedded/server/off` 三种模式；默认 embedded。
- `backend/app/core/config.py`：MLflow tracking、registry、experiment 配置。
- `backend/requirements-mlflow.txt`：训练/观测环境的兼容依赖集合。
- `backend/app/services/models.py`：训练、测试、推理成功后记录 Run。
- `.env.example`：增加配置示例。

当前记录内容：训练超参、指标、损失曲线、模型对象键、业务模型版本 ID；测试指标、混淆矩阵；推理模型版本、输入类型、延迟和结果 JSON。

MLflow 写入失败不会让业务 Job 失败，这是因为现阶段 MLflow 是增强能力而不是业务事务依赖。

## 当前嵌入式运行方式

默认配置为：

```env
MLFLOW_MODE=embedded
MLFLOW_TRACKING_URI=sqlite:///./data/mlflow.db
MLFLOW_ARTIFACT_ROOT=s3://aiwelding/mlflow-artifacts
```

FastAPI 内嵌 MLflow 客户端将 SQLite 用作 MLflow 元数据存储，并通过现有 MinIO 配置自动推导 S3 endpoint 和凭证。MLflow artifact 与业务原始文件分开，建议使用 `mlflow-artifacts` 前缀或独立 bucket。

切换为独立服务时只需：

```env
MLFLOW_MODE=server
MLFLOW_TRACKING_URI=http://mlflow:5000
```

业务 Job、数据库和适配层不需要改变。

注意：原后端的 `pandas>=3.0.5`、`pyarrow>=25.0.1` 与当前 MLflow 3.x 的依赖约束不兼容。本次已将项目统一降为 `pandas>=2.3,<3`、`pyarrow>=24,<25`，并把 `mlflow>=3.15,<4` 纳入主依赖；训练 worker 可复用同一组兼容版本。当前阶段默认使用 embedded 模式：SQLite 保存 MLflow 元数据、MinIO 保存 artifact；后续改为独立 Tracking Server 时只需设置 `MLFLOW_MODE=server` 和远程 URI。

## 第二阶段：真实训练接入时的改造

当前 `run_training` 已改为 CPU-only Torch 合成数据训练并写入真实 `state_dict` 权重；它仍是训练链路验证用的模拟数据，不代表焊接算法效果，因此暂不把该演示模型注册为生产模型。真实数据训练脚本接入后：

1. 在训练脚本中使用 `mlflow.start_run`，记录代码版本、数据集快照 ID、特征配置、随机种子、GPU/镜像信息。
2. 按实际框架调用公开模型日志 API，例如 `mlflow.pytorch.log_model` 或 `mlflow.sklearn.log_model`。
3. 用 `mlflow.register_model("runs:/<run_id>/model", registered_model_name)` 创建模型版本。
4. 把 MLflow `run_id`、registered model name/version 写入现有 `Job.result` 或新增关联字段。
5. 现有 `model_versions.status` 继续负责业务状态；MLflow alias/tag 作为外部协作和部署状态，不强行覆盖业务状态机。

## 其他项目的边界

- ClearML：需要统一数据集、训练队列和 Serving 时再评估；不与 MLflow 同时接管同一批训练任务。
- Kubeflow/KServe：只有在 Kubernetes/GPU 集群资源调度成为瓶颈时再引入，优先接 Pipeline 或 KServe 单组件。
- CVAT：作为图像/视频标注增强组件，通过 API 同步标注，不替换焊接数据和样本表。
- FiftyOne：作为测试评估的数据浏览器和预测分析工作台，不作为业务数据库。

## 许可证与合规

MLflow 主仓库为 Apache-2.0。部署时仍需核对实际安装版本及其依赖的许可证，并保留版权和 NOTICE 文件。生产环境应限制 artifact 权限，避免把敏感原始数据重复上传。
